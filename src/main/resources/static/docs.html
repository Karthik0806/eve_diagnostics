EVE Diagnostics API

Book diagnostic tests at centres, pay through a simulated provider, and receive provider updates through an idempotent webhook.

StackJava 21, Spring Boot 3.4, Spring Security, JPA, Flyway
DatabasePostgreSQL 16 (H2 in tests)
AuthJWT bearer tokens, roles USER and ADMIN
Base URLhttp://localhost:8080

Authentication

Log in to get a token, then send it on every protected request:

Authorization: Bearer <accessToken>
  • Tokens are HS256 JWTs carrying user id, email and role. Default lifetime is 60 minutes.
  • Public: signup, login, reading centres and tests, the webhook (signature-protected), health and docs.
  • Catalogue writes need ADMIN. A normal user gets 403; no token gets 401.
  • Users only see their own bookings and payments. Someone else's id returns 404, so ids cannot be probed.
  • Login and signup are rate limited per IP (default 20 per minute, then 429).

Booking and payment flow

  1. Browse centres (public). Each centre lists its tests with a price.
  2. Book with POST /bookings. The booking is PENDING and its amount is copied from the centre's price at that moment.
  3. Pay with POST /payments/. The mock provider answers SUCCESS or FAILED and the booking becomes CONFIRMED or FAILED.
  4. Retry a failed booking by paying again. A confirmed or cancelled booking cannot be paid.
  5. Webhook updates arrive from the provider later (see below).
PENDINGpay OKCONFIRMED
PENDINGpay failsFAILEDretryCONFIRMED / FAILED
PENDING / FAILED / CONFIRMEDcancelCANCELLED (final)

Payment outcome is random by default (APP_PAYMENT_SUCCESS_RATE). Send simulatedOutcome to force it. Add an Idempotency-Key header to make client retries safe: the same key returns the original payment with 200.

Webhook and idempotency

POST /payments/webhook/ is called by the payment provider. It is authenticated by a signature, not a JWT.

BODY='{"eventId":"evt_001","paymentReference":"pay_ab12...","status":"SUCCESS"}'
SIG=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "$WEBHOOK_SECRET" -hex | sed 's/^.* //')
curl -X POST localhost:8080/payments/webhook/ -H 'Content-Type: application/json' \
  -H "X-Webhook-Signature: $SIG" -d "$BODY"
resultMeaning
PROCESSEDState changed: payment FAILED to SUCCESS, booking CONFIRMED.
DUPLICATEThis eventId was already received. Nothing was touched.
NO_CHANGENew event, but the payment is already in that state.
IGNOREDNew event that must not apply: it would downgrade a success, the booking is cancelled, or the booking is already paid by another payment.

Why replays are safe

  • The event row is inserted first inside one transaction. event_id is UNIQUE in the database.
  • Two simultaneous deliveries race on that unique index. One wins, the other is answered as DUPLICATE.
  • The booking row is locked while its state changes, and a partial unique index allows only one SUCCESS payment per booking.
  • If processing fails (for example an unknown payment), everything rolls back including the event row, so the provider's retry still works.

Data model

TablePurpose and key rules
usersUnique email, BCrypt hash, role.
diagnostic_testsTest catalogue. Names are unique ignoring case.
diagnostic_centresName and location. Unique per name and location.
centre_testsWhich centre offers which test, at what price. Unique per centre and test.
bookingsUser, centre, test, appointment time, price snapshot, status, version column.
paymentsMany per booking. Unique provider reference and idempotency key, one success per booking.
webhook_eventsEvery accepted event. Unique event_id is the idempotency guard.

Money is NUMERIC(12,2). Times are UTC. The schema lives in db/migration/V1__init_schema.sql.

Errors

Every error has the same shape:

{ "timestamp": "2026-10-02T10:00:00Z", "status": 400, "error": "Bad Request",
  "message": "Validation failed", "path": "/bookings",
  "details": [ { "field": "appointmentTime", "message": "must be in the future" } ] }
StatusWhen
400Invalid fields, malformed JSON, bad enum or id format, past appointment time, bad webhook payload.
401Missing, invalid or expired token; wrong login; bad webhook signature.
403Logged in but not an admin on a catalogue write.
404Unknown id, someone else's booking or payment, test not offered by that centre, unknown payment reference.
409Duplicate email, test or centre; duplicate active booking; paying a confirmed or cancelled booking; already cancelled; reused idempotency key.
429Login or signup rate limit.
500Unexpected error. Details are logged, not returned.

Testing

mvn test

Integration tests run the real app with MockMvc against in-memory H2. They cover signup and login, admin-only catalogue changes, the booking and payment flow, ownership checks, and webhook replays, signatures and out-of-order events.
